the actual SQL, cross-checked against the replica's single-transaction

## Single-transaction consequence

If the whole chain applies in one transaction, every ACCESS EXCLUSIVE lock is held from the statement that takes it until the single final COMMIT after 00016 — locks are never released mid-transaction. The first AEL on drops lands at 00006's first statement, profiles is SRE-locked by 00006 section 1 and AEL-locked by section 6a, orders by section 2, seller_payments by section 0. So the effective full-block window (reads AND writes queued) on drops/profiles/orders/seller_payments is essentially the ENTIRE chain runtime — 00006 through 00016, including the 00013 median seed and 00016 cron scheduling — not the microseconds each catalog statement needs. From 00008's sequence REVOKE onward, processed_events INSERTs (webhook idempotency writes) also block until COMMIT. Every read that arrives after the AEL is queued behind it and stalls, so 'reads still work during the instant DDL' is false in this mode: one held AEL blocks all subsequent reads of that table for the rest of the chain. With ~4 rows total the runtime is dominated by catalog churn (~200 DDL statements) and should be low single-digit seconds, so the absolute window is small — but a single error or deadlock anywhere rolls the entire chain back (atomically and re-runnably, which is the compensating virtue). Note the standard Supabase paths (supabase db push, apply_migration) wrap each FILE in its own transaction rather than the whole chain; even then 00006 and 00007 individually hold AEL on drops/profiles/orders for their full per-file runtime, so the per-file picture is the same shape, just shorter.

## Deadlock risks and mitigations

Three concrete patterns, all resolved by pausing webhooks + lock_timeout during the window. (1) Incremental multi-table acquisition: the chain locks, in order, drops (AEL) -> seller_payments (SHARE then AEL) -> profiles (SRE at discount_codes FK, upgraded to AEL at 00006 6a) -> orders (AEL) -> auth.users/videos (SRE, 00007). A concurrent webhook transaction touching the same tables in a different order (checkout: INSERT orders + decrement_inventory on drops + read profiles/seller_payments; account.updated: UPDATE seller_payments) can form a cycle — e.g. migration holds AEL(seller_payments) from section 0 and requests AEL(profiles) at 6a, while a webhook txn holds ACCESS SHARE(profiles) (admitted through the migration's earlier SRE, which does not block reads) and is waiting to write seller_payments. Deadlock detector fires at ~1s and kills one side; if the MIGRATION is the victim, the entire single-transaction chain rolls back (safely, but it must be re-run). (2) Same-table lock upgrade: profiles goes SRE (00006 section 1 FK) -> AEL (section 6a); seller_payments goes SHARE (CREATE INDEX IF NOT EXISTS) -> AEL (DROP TRIGGER) one statement later. The weaker lock admits concurrent ACCESS SHARE readers, and any such reader that then waits on a migration-held lock elsewhere (e.g. the AEL on drops or orders) closes the cycle — this is exactly the SHARE-then-AEL vs concurrent-ROW EXCLUSIVE shape the task flags; the writer variant cannot interleave (SHARE already conflicts with ROW EXCLUSIVE) but the reader variant can. (3) Queue pile-up (not a deadlock but the operational twin): a waiting AEL blocks every LATER lock request including plain SELECTs, so if any long transaction holds drops/profiles when the migration starts, the storefront freezes behind the queued AEL for as long as that transaction runs — lock_timeout converts this from an outage into a fast, retryable failure. Probability of all three is near zero at this traffic level, and the blast radius is bounded to 'chain rolls back, re-run', but the mitigations are free. Also note 00007's SET CONSTRAINTS video_products_max_five IMMEDIATE: not a deadlock, but without it the queued DEFERRABLE trigger event makes the later ALTER TABLE video_products fail ('pending trigger events') and aborts the whole transaction — it is already correctly placed in the file.

## Maintenance-window verdict

Strictly by lock math, no maintenance window is needed: every scan, validation, backfill, and index build in the chain is bounded by tables of 0–1 rows, so the total blocking window is realistically 1–5 seconds even with the whole chain in one transaction. Take a short window anyway (2–5 quiet minutes), for reasons that are not about lock duration: (1) at COMMIT, public.drops stops existing and profiles/orders grants change shape — any app instance still running pre-migration code breaks instantly, so the migration and the app deploy must land together, and a window is the cheapest way to guarantee that ordering; (2) pausing/deferring the Stripe, Mux, and EasyPost webhook endpoints for those minutes removes the only realistic lock counterparties (they retry, so nothing is lost); (3) run with lock_timeout set (5–10s) and statement-level retry, so that if some stray long-running transaction is holding drops or profiles, the migration fails fast and re-runs instead of queuing an AEL that stalls every subsequent storefront read behind it. Plain terms: the database work is seconds; the window is for cutover coordination and deadlock elimination, and it costs almost nothing at near-zero traffic.
